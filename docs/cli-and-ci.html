Automation

Command line and CI

Run load tests and collection runs from a pipeline and fail the build when an API breaks or gets slower.

Tip Setting this up for the first time? Follow From the app to your pipeline — step by step, with a ready pipeline file. This page is the reference.

Tip The command line is on npm as apitestcenter. Run it with npx apitestcenter … — nothing to install first. Build and save your requests in the desktop app, then run them here.

Two commands

# Send every request in a collection once and check each one
npx apitestcenter suite "Orders API" --env UAT --junit results.xml

# Run a saved request's load test with pass/fail targets
npx apitestcenter run "Orders API/List orders" --env UAT --preset smoke --p95 500 --errors 1 --junit results.xml

Both use the same engine, checks, and rules as the app, so a pipeline run and a run in the app mean the same thing. They read your saved requests, environments, and collection run order. Two names for the same tool: apitestcenter and the short atc.

How you run itCommand
No install (CI, a quick try)npx apitestcenter suite … — always use the full name with npx: npx atc would look for a different npm package called "atc"
Installed once on your computernpm install -g apitestcenter, then atc suite … (or apitestcenter suite …)
In a project (devDependency)npm install -D apitestcenter, then npx atc suite … inside that project

Requirements: Node.js 20 or later. suite needs nothing else. run uses k6: if it is not installed, the first run downloads the official k6 release once, checks it against k6's published checksums, and keeps it in a cache folder. Set K6_BIN to use your own k6.

Exit codes

Codeatc suiteatc run
0Every request passedEvery target met and the result is not failing
1A request failed or could not runA target was missed or the result failed
2Could not start: unknown collection or environment, bad argumentsCould not start: bad arguments, a missing variable, the first request not 2xx, k6 could not be found or downloaded

A pipeline step that runs atc fails on any code other than 0 — that is how a broken or slow API stops a release.

Options

OptionMeaning
--data <folder>Where your saved requests are — a copy of the app's data folder in your repository (default: this computer's APITestCenter folder)
--env <name>The environment for {{variables}}
--var key=valueSet or override a variable (repeatable) — use this for CI secrets
--junit <file> · --html <file> · --json <file>Write the report
--stop-on-failsuite: stop at the first request that fails
`--preset smoke\average\stress\spike\soak`run: start from a preset
--vus, --duration, --rps, --max-vusrun: change the load
--p95 <ms>, --p99 <ms>, --errors <%>, --checks <%>, --abortrun: pass/fail targets; --abort stops early when one is clearly missed
--baseline <file>run: compare with a saved report and fail if it got slower — see Did it get slower?
--max-slower <percent>run: how much slower than the baseline is allowed (default 10)
--save-baseline <file>run: save this run as the baseline for later runs
--quietOnly the final summary
--versionPrint the version

Did it get slower?

Fixed goals (--p95 500) catch an API that is slow. A baseline catches an API that got slower than it was — even while it is still under the goal.

# On your main branch: save a good run as the baseline
npx apitestcenter run "Orders API/List orders" --data api-tests --env UAT --save-baseline api-tests/baseline.json

# On every deployment: compare with it, and fail if p95 is more than 10% slower
npx apitestcenter run "Orders API/List orders" --data api-tests --env UAT --baseline api-tests/baseline.json --max-slower 10
compared with baseline “List orders” (2026-10-02)
  After is 18% slower: 95% of requests within 142 ms → 168 ms. That is more than normal run-to-run variation.
  ✕ 18% slower than the baseline (p95 142 ms → 168 ms), more than the 10% allowed

The run fails (exit code 1) when p95 is slower by more than --max-slower percent (default 10), or when more requests fail than in the baseline. Differences under 5% or 10 ms count as the same. If the baseline used different load or a different request, the comparison is skipped instead of judged. With --junit, the comparison is its own test case, so the reason shows in your CI's test results.

Any exported JSON report works as a baseline — from the app (Export → JSON) or from --save-baseline.

Secrets in a pipeline

Secrets saved in the app are encrypted with your computer's key, so a build agent cannot read them. Write {{token}} in the request and pass the value from your CI's secret store:

npx apitestcenter suite "Orders API" --env UAT --var token=$ORDERS_TOKEN --junit results.xml

Examples

GitHub Actions

- name: API checks
  run: npx apitestcenter suite "Orders API" --data api-tests --env UAT --var token=${{ secrets.ORDERS_TOKEN }} --junit atc.xml
- uses: actions/upload-artifact@v4
  if: always()
  with: { name: api-checks, path: atc.xml }

GitLab CI

api-checks:
  script:
    - npx apitestcenter suite "Orders API" --data api-tests --env UAT --var token=$ORDERS_TOKEN --junit atc.xml
  artifacts:
    when: always
    reports:
      junit: atc.xml

Azure DevOps

- script: npx apitestcenter suite "Orders API" --data api-tests --env UAT --var token=$(ORDERS_TOKEN) --junit atc.xml
- task: PublishTestResults@2
  condition: always()
  inputs: { testResultsFormat: JUnit, testResultsFiles: atc.xml }

Your requests in the repository

A pipeline can't see the app on your computer, so keep a copy of what it needs in your repository. The easy way: Run collection → Download for CI gives you a zip with the collection (no secrets) and a ready pipeline — see step 3 of the walkthrough. By hand: copy the requests folder, environments.json, and suites.json from your data folder (About → Open folder) into, say, api-tests/, and run with --data api-tests.

Secret values are never in those files, so they are safe to commit; pass secrets with --var. Update the copy when you change requests in the app.
