Automation

Command line and CI

Run load tests and collection runs from a pipeline and fail the build when an API breaks or gets slower.

Note The command-line tool is being published to npm as apitestcenter — run it with npx apitestcenter …, no install step. Until it appears on npmjs.com/package/apitestcenter, this page describes how it works so you can plan.

Two commands

# Send every request in a collection once and check each one
atc suite "Orders API" --env UAT --junit results.xml

# Run a saved request's load test with pass/fail targets
atc run "Orders API/List orders" --env UAT --preset smoke --p95 500 --errors 1 --junit results.xml

Both use the same engine, checks, and rules as the app, so a pipeline run and a run in the app mean the same thing. They read your saved requests, environments, and collection run order. atc is the short name; apitestcenter works too.

Requirements: Node.js 20 or later. suite needs nothing else. run uses k6: if it is not installed, the first run downloads the official k6 release once, checks it against k6's published checksums, and keeps it in a cache folder. Set K6_BIN to use your own k6.

Exit codes

Codeatc suiteatc run
0Every request passedEvery target met and the result is not failing
1A request failed or could not runA target was missed or the result failed
2Could not start: unknown collection or environment, bad argumentsCould not start: bad arguments, a missing variable, the first request not 2xx, k6 could not be found or downloaded

A pipeline step that runs atc fails on any code other than 0 — that is how a broken or slow API stops a release.

Options

OptionMeaning
--data <folder>Where your saved requests are — a copy of the app's data folder in your repository (default: this computer's APITestCenter folder)
--env <name>The environment for {{variables}}
--var key=valueSet or override a variable (repeatable) — use this for CI secrets
--junit <file> · --html <file> · --json <file>Write the report
--stop-on-failsuite: stop at the first request that fails
`--preset smoke\average\stress\spike\soak`run: start from a preset
--vus, --duration, --rps, --max-vusrun: change the load
--p95 <ms>, --p99 <ms>, --errors <%>, --checks <%>, --abortrun: pass/fail targets; --abort stops early when one is clearly missed
--quietOnly the final summary
--versionPrint the version

Secrets in a pipeline

Secrets saved in the app are encrypted with your computer's key, so a build agent cannot read them. Write {{token}} in the request and pass the value from your CI's secret store:

atc suite "Orders API" --env UAT --var token=$ORDERS_TOKEN --junit results.xml

Examples

GitHub Actions

- name: API checks
  run: npx apitestcenter suite "Orders API" --data api-tests --env UAT --var token=${{ secrets.ORDERS_TOKEN }} --junit atc.xml
- uses: actions/upload-artifact@v4
  if: always()
  with: { name: api-checks, path: atc.xml }

GitLab CI

api-checks:
  script:
    - npx apitestcenter suite "Orders API" --data api-tests --env UAT --var token=$ORDERS_TOKEN --junit atc.xml
  artifacts:
    when: always
    reports:
      junit: atc.xml

Azure DevOps

- script: npx apitestcenter suite "Orders API" --data api-tests --env UAT --var token=$(ORDERS_TOKEN) --junit atc.xml
- task: PublishTestResults@2
  condition: always()
  inputs: { testResultsFormat: JUnit, testResultsFiles: atc.xml }

Your requests in the repository

A pipeline can't see the app on your computer, so keep a copy of what it needs in your repository:

  1. In the app, About → Open folder.
  2. Copy the requests folder (or just the collections you need, inside it), environments.json, and suites.json (the run order) into a folder in your repository, for example api-tests/.
  3. Run with --data api-tests.

Secret values are never in those files, so they are safe to commit; pass secrets with --var. Update the copy when you change requests in the app.
