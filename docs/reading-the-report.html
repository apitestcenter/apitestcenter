Results

Reading the report

What every number in a load-test report means, how the app decides pass or fail, and what failing status codes like 429 or 503 are telling you.

The result

At the top of every report is the Result — the app's plain summary:

  • Looks healthy — nothing worrying at this load.
  • Usable, with caveats — read the lines underneath before you rely on it.
  • Not production-ready at this load — something clearly failed.
  • Blocked by a rate limit or firewall — most requests were refused on purpose (429 or 403). The numbers show that limit, not your API's speed.

Underneath, each part is judged on its own:

PartWhat it looks at
ErrorsThe share of failed requests, and what the most common failure means
LatencyHow long 95% of requests took (p95) — not judged when most responses were errors
StabilityWhether response times grew from the start of the run to the end
CapacitySigns of overload: timeouts, 5xx errors, requests that could not be sent, being refused
ChecksThe share of answers that passed your checks

Without your own goals, the app uses starting rules: fewer than 1% failures is fine and 5% fails; 95% of requests within 500 ms is fine and 2 seconds fails. Set your own as soon as you know what your API promises.

Note When more than half of the responses failed, the response-time numbers mostly describe error replies — which come back almost instantly. The report then shows them without a green or red colour and says so. Where it can, it also shows how fast the API was while requests were still succeeding.

The charts

  • Response time — p50, p95, and p99 second by second. A line that climbs means the API is slowing down.
  • Requests per second — how much load was actually delivered.
  • Responses by outcome — 2xx, 4xx, 5xx, and no answer, second by second. The moment the colours change is the moment trouble started.
  • Where the time went — waiting for a connection, DNS, TCP, TLS, sending, server time, download. High connection times point at the network or your computer; high server time points at the API.
  • Response time distribution and the heatmap — how response times were spread, not just their averages.

Arrange the report your way with Views: add, remove, resize, and reorder widgets, add headings and single-number tiles. By topic groups them into Speed, Reliability, and Load.

What happened — the written debrief

The HTML export starts with What happened in this run: the load, the speed, errors and when they started, where the time went, and whether the API looked near its limit — followed by suggested next steps. It is written by fixed rules from the measured numbers, so the same run always gets the same words.

Failing status codes, in plain words

StatusMeansUsually
no answerTimeout, refused connection, or network problemThe API is down or overloaded, or a firewall drops the traffic
400Bad requestSomething in the request is wrong
401Not signed inMissing or expired token — see Run first
403ForbiddenRefused on purpose, often by a firewall that blocks heavy traffic
404Not foundWrong address
429Too many requestsA rate limit: the server or its CDN is slowing you down on purpose
500Server errorThe API crashed or hit a bug — look at its logs
502 / 504Bad gateway / gateway timeoutA proxy in front of the API couldn't reach it, or waited too long
503UnavailableThe API is overloaded or down

If failures start at a certain moment, the debrief says when, at what load, and whether they stopped when the load dropped. Failures that continue after the load drops are typical of a rate limit or firewall that blocks a caller for a while. See Troubleshooting.
