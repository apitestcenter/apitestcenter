Testing APIs

Checks

Rules for a correct answer. A fast answer with an error inside should still fail — checks make sure it does.

New to this? The lessons explain the ideas behind this page: what to check, and how strict to be, and contracts and schemas.

Open the Checks tab and add rules. Each Send shows ✓ or ✕ for every rule, and a performance test applies them to every request, so the report says what share of answers were correct — not just fast.

Kinds of checks

CheckPasses whenExample
StatusThe status matches. Use one code, several, a range, or a class.200 · 200, 201 · 200-299 · 2xx
JSON fieldA field exists or not; equals, does not equal, or contains a value; is more or less than a number; matches a pattern; is of a type; has a length.data.items[0].id exists · errors does not exist · total is more than 0 · items has length >0 · id is of type integer
Body textThe answer contains — or does not contain — some text, matches a pattern, or is valid JSON.does not contain error · is valid JSON
HeaderA response header exists or not, equals, contains, or matches a pattern.content-type contains json · x-powered-by does not exist
Response timeThe answer arrived within a time, in milliseconds.within 500 ms
JSON schemaThe whole answer matches a JSON Schema.see below

JSON paths start from the top of the answer: name, data.user.id, items[2].price. A leading $. is fine too.

Types are string, number, integer (a whole number), boolean, array, object and null. Length counts the items of a list, the characters of a text, or the keys of an object; write 3, >0, >=1, <10, <=10 or !=0. Patterns are regular expressions, like ^ord_\d+$.

When a check fails, Send says why next to it — got 404, is "pending", not found — and so does the collection run, in the app and in CI.

JSON schema

A schema check makes sure every answer has the right shape: the fields that must be there, and the type of each — a whole contract in one check, instead of one check per field.

  1. Send the request once.
  2. Checks → Add JSON schema → Make it from the last response. It writes a schema the answer matches: every field it had is required, with its type. A list's items take the fields every item had.
  3. Loosen or tighten it — remove a field from required when it may be missing, add "nullable": true or "type": ["string", "null"] when it may be empty, add "enum", "minimum" or "pattern" for allowed values.

When an answer differs, the check says where: $.items[0].id should be integer (it is string), $ should have id.

Supported: type (with nullable), enum, const, properties, required, additionalProperties, items, minItems/maxItems, minLength/maxLength, pattern, minimum/maximum and their exclusive forms, allOf/anyOf/oneOf, and $ref to the schema's own definitions or $defs. Other keywords — format, say — are ignored. Importing an OpenAPI or Swagger file adds a schema check like this to each request, from the file's response schemas ($refs to its own components work; outside files don't) — or, by default, keeps the file as the collection's API description, which checks every answer against it, error answers too: see Contract tests.

In a performance test the schema is checked on every answer; a large schema on a fast API costs a little CPU on this computer.

How checks affect results

  • Send: the Checks badge shows how many passed (for example 2/3), and each rule is listed in the response.
  • Performance test: the report shows the share of passing checks and which check failed most often. By default the result fails if fewer than 99% of checks pass; you can change that under Goals.
  • Collection run: a request with checks passes only when all of them pass. A request without checks passes on any 2xx or 3xx status.

Tip Start with a status check and one JSON field check on something that must be there. That catches most “fast but wrong” answers — like a 200 with an error message inside.
