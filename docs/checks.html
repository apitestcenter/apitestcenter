Testing APIs

Checks

Rules for a correct answer. A fast answer with an error inside should still fail — checks make sure it does.

Open the Checks tab and add rules. Each Send shows ✓ or ✕ for every rule, and a load test applies them to every request, so the report says what share of answers were correct — not just fast.

Kinds of checks

CheckPasses whenExample
StatusThe status matches. Use one code, several, a range, or a class.200 · 200, 201 · 200-299 · 2xx
JSON fieldA field exists, equals, does not equal, or contains a value.data.items[0].id exists · status equals active
Body textThe answer contains — or does not contain — some text.does not contain error
HeaderA response header exists, equals, or contains a value.content-type contains json
Response timeThe answer arrived within a time, in milliseconds.within 500 ms

JSON paths start from the top of the answer: name, data.user.id, items[2].price. A leading $. is fine too.

How checks affect results

  • Send: the Checks badge shows how many passed (for example 2/3), and each rule is listed in the response.
  • Load test: the report shows the share of passing checks and which check failed most often. By default the result fails if fewer than 99% of checks pass; you can change that under Goals.
  • Collection run: a request with checks passes only when all of them pass. A request without checks passes on any 2xx or 3xx status.

Tip Start with a status check and one JSON field check on something that must be there. That catches most “fast but wrong” answers — like a 200 with an error message inside.
