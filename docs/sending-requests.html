Testing APIs

Sending requests

Build a request, send it once, read the answer, and keep it in a collection — or bring your requests in from Postman, OpenAPI, or curl.

The request bar

Pick the method (GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS), type or paste the URL, and press Send (Ctrl+Enter).

You can paste more than a URL:

  • A curl command — for example from your browser's DevTools (Copy as cURL). The method, headers, body, and auth are filled in for you.
  • A URL with a query string — the parameters appear in the Params tab, where you can edit them one by one.
  • A path, like /orders — pick the server from the Base URL picker next to the method. See Choosing a base URL.

Press / to jump to the URL from anywhere on the page.

The body

Choose None, JSON, or Text.

  • JSON is checked as you type: Valid JSON, or the error and where it is. Format JSON tidies the body with neat indentation. An empty JSON body sends {}.
  • Text is sent exactly as you type it.

OAuth 1.0 (NetSuite and older APIs)

Some APIs sign every request with two pairs of keys instead of using a token — NetSuite's token-based authentication (TBA), and older services. Choose Auth type → OAuth 1.0:

  • Consumer key and Consumer secret — from the integration record (in NetSuite: Integration);
  • Token and Token secret — from the access token (in NetSuite: Access Token);
  • Signature method — HMAC-SHA256 (NetSuite, and most current APIs), HMAC-SHA1 for older ones, or PLAINTEXT (https only);
  • Realm — for NetSuite, your account ID, like 1234567 or 1234567_SB1 for a sandbox;
  • Send the signature in — the Header (Authorization: OAuth …, the usual) or the Query.

Each request gets a fresh nonce, timestamp and signature, over its method, address, query and — for a form body — the form fields. Load tests sign every request the same way inside k6. Use {{variables}} for the four keys to keep them in an environment.

Digest and NTLM

Older and Windows-based services often sign in with a challenge: the server answers the first request with 401 and a challenge, and the next request proves the password without sending it.

  • Digest — Username and Password. MD5 and SHA-256 (also the -sess variants) are supported.
  • NTLM — Windows sign-in (IIS, SharePoint, internal APIs): Username, Password, and Domain. You can also type CORP\ann as the username. The app uses NTLMv2, and keeps the short sign-in exchange on one connection, as NTLM requires.

On Send you see only the final answer. In load tests, k6 repeats the exchange for every request; those extra 401 replies are not counted as requests, so the numbers, times and error rate describe the real answers. If every request is refused, the run fails with Every request was refused with 401 — check the username, password and domain.

AWS Signature (SigV4)

For AWS endpoints that check a signature instead of a token — API Gateway with IAM auth, S3, Lambda function URLs, OpenSearch. Choose Auth type → AWS Signature and fill in:

  • Access key ID and Secret access key — from an IAM user or role;
  • Region — like eu-west-1;
  • Service — execute-api for API Gateway, s3, lambda for function URLs, es for OpenSearch;
  • Session token — only for temporary credentials (from aws sts, SSO, or a role).

Every request is signed just before it goes out, over its address, query, x-amz-* headers and body. In load tests each request gets a fresh signature, after any test data is filled in. For S3 the body hash is sent as x-amz-content-sha256, as S3 requires. Write {{awsSecretAccessKey}} to take the key from an environment or, in CI, from --var. A signature AWS rejects comes back as 403 with AWS's own explanation in the answer.

JWT signed by the app

When an API accepts a JSON Web Token you can create yourself — signed with a shared secret or your private key — the app can sign it for you. Choose Auth type → JWT (signed here):

FieldWhat to put
AlgorithmHS256/384/512 with a shared Secret; RS256/384/512, PS256, or ES256/384/512 with a Private key (PEM) — paste it or Load a .pem file
Claims (JSON)The token's contents, like { "sub": "user-1", "aud": "orders-api" }. iat (issued now) and exp (now + Valid for) are added unless you set them. {{variables}} work here.
Valid for (minutes)How long each token lasts
Key ID (kid)Optional, for APIs that pick the key by id
Header and PrefixWhere the token goes: Authorization with Bearer by default; empty prefix sends the token alone (e.g. X-Api-Token)

Every Send signs a fresh token. In load tests the app signs the tokens before the test starts — a series of them when the test runs longer than one token lasts, each issued when it starts being used and replaced at 80% of its life — so no request carries an expired token, and the private key never goes to the load generator. Claims are filled from the environment; values from test data don't change the claims per user.

Cookies

Like a browser, the app keeps the cookies an API sets and sends them back to it on later requests — so a site that signs in with a login form and a session cookie just works: send the login once (or make it the Run first request), and the requests after it are signed in. Cookies set on a login's redirect are kept too.

Cookies go only where they belong: to the site that set them (and its subdomains, if it said so), under their path, Secure ones only over https, and not after they expire. A cookie the server expires is forgotten.

Open See cookies on the Settings tab, or Cookies in the command palette, to see them per site — values are shortened, because a session cookie is a credential — and delete one, a site's, or all. Cookies are kept encrypted with your other secrets; session cookies (no expiry) are gone when the app closes. Turn Use the cookie jar off on a request to send only a Cookie header you add yourself.

In load tests the session cookies go with every request (passed to k6 privately, never saved with the run), and each simulated user then keeps the cookies the API sets for it.

Client certificates (mutual TLS)

Some APIs ask the caller for a certificate as well (mutual TLS, mTLS). Client certificates are set per host, not per request: every request to that host presents it — on Send, in Run first, collection runs, Compare and load tests — together with whatever Auth the request uses.

Open Manage certificates on the Settings tab, or Client certificates (mutual TLS) in the command palette. To add one:

  1. Host — api.example.com; *.example.com for every subdomain (one level); add a port, api.example.com:8443, to use it on that port only. When several match, the exact host wins over a wildcard.
  2. The format: Certificate + key (PEM, CRT) — choose both files — or PFX / P12 — one file.
  3. Passphrase, if the key or the PFX file has one.
  4. Add certificate. The app checks it first: The passphrase is wrong or The private key doesn't belong to this certificate means nothing was saved.

The list shows each certificate's host, name (CN), format, and how long it is valid — an expired one is marked in red. The bin removes it. The Settings tab says the one for \.example.com* when a request uses one, none for this host, or only for https addresses (plain http never sends a certificate).

The public certificate is kept in certificates.json in your data folder; the private key, a PFX file and the passphrase are encrypted with your other secrets and never exported. An OAuth token URL that wants a certificate gets it too.

Trusted certificate authorities. The desktop app trusts the certificates your computer trusts — so servers signed by your company's CA, and a company proxy that inspects https traffic, work without any setting. For a CA your computer doesn't know, open Manage certificates and Add a CA certificate (.pem or .crt; a file with several is fine). The list shows each CA's name and how long it is valid; the bin removes it. Only CA certificates are accepted — not a server's own certificate. Requests then check servers against these CAs instead of skipping the check. In load tests: on Linux, k6 is given the same CAs. On Windows and macOS k6 can't load extra CAs, so when a server needs one of yours, the app checks its certificate with your CA once before the test and k6 skips its own check during the test.

Reading the answer

The Response panel shows:

  • the status (200 OK, 404 Not Found…), the time, the size, and the content type;
  • Body — see below;
  • Headers — response headers. Copy all copies them as Name: value lines. Sign-in headers such as Authorization and Set-Cookie are hidden as [redacted];
  • Checks — each rule with ✓ or ✕.

The Body tab has these views:

  • Pretty formats JSON with colours.
  • Raw shows the answer exactly as it came.
  • Preview — for HTML answers only — shows the page as a browser would. It is sandboxed: scripts on the page do not run.

The buttons on the right search the body (Ctrl+F; Enter and Shift+Enter move between matches), turn line wrapping on or off, copy the body, and download it as a file.

The app shows the first 64 KB of a large body; it says First 64 KB shown, and the size ends with +. Checks and saved values still use the whole answer.

If the request used Run first, a line under the status says what ran first and which values it found. When the request fails without an answer — for example Connection refused or Timed out — the panel says what that usually means and what to try.

Saving requests and collections

Press Ctrl+S (or Save request) to keep a request. Give it a Name and, optionally, a Collection — a folder that groups related requests, like Orders API. Pick an existing one from the list or type a new name. Use / for a folder inside another: Orders API/Admin. Folders nest up to 6 levels.

Once a request is saved, its collection and name appear under the URL. When you change it, ● unsaved appears next to the name: press Save (Ctrl+S) to update it, or Save as… to keep the original and save a copy.

Saved requests are plain files on your computer. Secrets in them (tokens, passwords, API keys) are kept encrypted, never in the file — see Privacy and your data.

The Saved requests panel

Saved requests are listed on the left, in their folders. Click one to open it. Search requests finds them by name, folder, URL, or method.

Folders: sign in once

A folder can pass settings down to every request inside it, and inside its subfolders. Open them with ⋯ → Folder settings on the folder. A 🔑 next to a folder's name means it sets auth.

TabWhat the requests inside get
AuthThe folder's sign-in. Requests set to Auth → From folder use it — that's the default for new requests, so you type a token once instead of in every request. From parent passes on the auth of the folder above; None stops it.
HeadersSent with every request inside. A request's own header with the same name — or an inner folder's — replaces it.
VariablesDefaults for {{name}}. The chosen environment wins when it has the same name, so a folder can hold basePath = /v2 while the environment picks the server. See Which value wins.

On a request, Auth → From folder says where its auth comes from (Uses the Bearer token set on the folder Orders API), and the Headers tab lists the headers it gets from its folders. A request that sets its own auth type keeps it.

Folder secrets — a token, a password, an OAuth client secret, a secret variable — are kept encrypted on this computer, like a request's, never in the folder's file (_folder.json inside the folder). Folder settings apply everywhere a request is sent: Send, load tests, Compare, Run first, collection runs, and the command line.

OAuth 2.0

Choose Auth → OAuth 2.0 on a request — or, better, on a folder, so every request inside signs in once. The app gets the token from your sign-in server, sends it as Authorization: Bearer …, keeps it encrypted on this computer until it runs out, and gets a new one by itself.

Grant typeUse it forYou fill in
Client credentialsService to service — the app signs in as itself. The best choice for load tests.Token URL, Client ID, Client secret, Scope
PasswordSigning in as a user with a username and password (older APIs, test accounts)The same, plus Username and Password
Authorization codeSigning in as a user in the browser, onceAuthorization URL, Token URL, Client ID (and Client secret if it has one), Scope, Redirect URL, PKCE (on by default)

Two more grants, and one more way for the client to prove itself (choose them under Grant type and More):

ChoiceForYou fill in
JWT bearer grantSalesforce, Google service accounts — no browser, no user passwordPrivate key (PEM), Issuer (defaults to the client ID), Subject (the user, if the API wants one), Audience (defaults to the token URL), and Extra claims as JSON (Google: { "scope": "…" })
SAML bearer grantSAP SuccessFactorsEither SuccessFactors builds it — the Assertion URL (https://<your API server>/oauth/idp), User ID, Company ID and the Private key of your OAuth client — or I have an assertion and paste it (base64). The builds it way sends your private key to SuccessFactors, as SAP documents; for production, prefer an assertion from your identity provider.
More → Signed with a private key (client assertion, private_key_jwt)Azure AD with a certificate, Okta, KeycloakPrivate key, and the Certificate if Azure AD should find the key by its thumbprint (x5t); no client secret

The private key is kept encrypted. Signed assertions last five minutes; in load tests the app signs the ones each simulated user needs to renew its token ahead of time, so the key never goes to the load generator. SuccessFactors builds each SAML assertion on its side, so its tokens (valid about a day) are not renewed during a load test.

For Authorization code, add the Redirect URL — http://127.0.0.1:53682/callback unless you change it — to your OAuth app exactly as shown. It must be on this computer. Then press Sign in in the browser: your browser opens the sign-in page, and after you sign in the app catches the answer and keeps the token and its refresh token. Later requests, load tests and runs refresh it without asking. If the refresh stops working, press Sign in again.

The panel under the settings shows the token: Token ready · expires in 54 min · orders:read. Get new token fetches one now (client credentials and password); the bin forgets it. Errors from the server are explained — for example invalid_client — check the client ID and secret, and whether they go in a header or the body.

Under More:

  • Send the client ID and secret — In a Basic auth header (the default) or In the request body. Servers differ; if you get invalid_client, try the other.
  • Extra fields — added to the token request and the sign-in page, such as audience or resource.

Every field takes {{variables}}, so the client secret can come from an environment or, in CI, from --var clientSecret=…. Changing the client, user, secret or scope gets a new token.

In load tests the token is fetched once before the test starts. If the test runs longer than the token lasts, each simulated user gets a new one shortly before it runs out — client credentials and password ask the server again; authorization code uses the refresh token. Those token requests are counted in the test's numbers (one per simulated user per token lifetime).

On the command line, OAuth works the same way. Authorization code needs the browser once: sign in in the app (or npx apitestcenter ui) with the same data folder, and runs on that computer reuse and refresh the token. In CI, use client credentials.

Importing from Postman, OpenAPI, or Swagger

Click Import (the arrow icon in the Saved requests panel), or choose Import from Postman or OpenAPI in the command palette. Then Choose a file, or drop it on the dialog:

  • Postman collections (v2.0 and v2.1) and Postman environments;
  • OpenAPI 3 and Swagger 2 files, as JSON or YAML (.json, .yaml, .yml).

Files can be up to 20 MB. No file? Click Or paste it instead, paste the JSON or YAML, and press Read it.

Before anything is saved, the app lists what it found — requests, folders, environments — and anything it could not bring across (for example, Postman scripts). Auth carries over for Bearer, Basic, API key, Digest, NTLM, OAuth 1.0, AWS Signature and JWT (OAuth 2.0 settings must be entered again). Postman folders stay folders inside the collection, and the auth and variables set on a Postman collection or folder become that folder's settings, which its requests inherit — as in Postman. Variables in requests stay as {{variables}}.

Put the requests in collection names the top folder they go into. It starts as the file's title; change it if you like (up to 60 characters). Folders inside it keep their names. If that collection already has requests, they are kept and the new ones are added.

Your current requests are not changed. Press Import to save — the button says how many requests and environments it will add.

Tip After importing an OpenAPI file, set its server address once as a variable in an environment, and every imported request uses it.
