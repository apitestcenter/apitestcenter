Testing APIs

Load tests

Send the same request many times at once to see how fast it stays and whether it holds up — with presets, simulated users or a fixed request rate, and goals.

A load test sends your request again and again, from many simulated users at the same time, for a while. It runs on your computer with k6, the open-source load-testing engine bundled with the app.

Press Send first: before a load test starts, the app sends the request once and stops if the answer is not 2xx — so a wrong token never turns into thousands of failed requests.

Simulated users or requests per second

Drive load by chooses how the load is measured:

  • Simulated users — each user sends a request, waits for the answer, optionally pauses (think time), and sends the next. A slow API therefore receives fewer requests. Good for “what do 50 people feel?”
  • Requests per second — the app keeps a fixed rate, whatever the API does, adding users as needed up to Max simulated users. This is the honest way to find how much an API can take. If the API is too slow to keep up, the report shows Requests not sent.

Warning With simulated users and no think time, each user fires its next request the moment the last one returns. A few dozen users can mean thousands of requests per second. Public sites and APIs behind a CDN or firewall will usually answer with 429 or 403 and may block you for a while. Use Requests per second with a modest rate, or test a staging server.

Shape over time

  • Ramp · hold · down — go up to the target over Ramp up, stay for Hold for, come down over Ramp down.
  • Step by step — a list of stages; each moves steadily to its target over its duration. Repeat a target to hold it.

Think time (and Random extra) adds a pause between a user's requests, like a person reading the page. It does not apply when holding a request rate.

Goals (pass or fail)

By default the app judges a run with starting rules (fewer than 1% failed requests, 95% of requests within 500 ms). The Goals tab lets you set your own:

  • p95 must stay under (ms) and, optionally, p99 must stay under (ms);
  • Error rate must stay under (%);
  • Checks must pass at least (%) — used when the request has checks;
  • Stop the test early if a target is clearly missed — after a 10-second warm-up, the run ends as soon as a goal fails.

Goals are remembered on this computer, drive the result and the report's colours, and are sent to k6 as thresholds — so a CI run fails the same way.

While it runs

The Load report fills in live: requests per second, response times, failures, and users, second by second. Stop ends it early; what ran so far is kept. Ask for a notification with Notify me when done, and carry on with other work.

Every finished run is saved in History. Reading the result: Reading the report.

Good habits

  1. Smoke first. A tiny run catches a wrong URL or token before a big one.
  2. Change one thing at a time — users, or the API version — and compare with a reference run.
  3. Test from close to the API when you can. Your network and computer are part of every number.
  4. Only test what you're allowed to. Heavy load on someone else's system can look like an attack.
